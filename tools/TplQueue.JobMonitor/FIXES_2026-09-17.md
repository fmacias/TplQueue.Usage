## 2. Important semantic issue discovered afterwards

The frontend contract was improved to require `channel`, but the current TplQueue observer contract (`IJobEvent`) does not necessarily expose the real execution channel.

The first Blazor integration therefore had to invent/present a channel outside the actual runtime execution-slot ownership. 

That is not the desired final behavior.

### Correct semantic

A channel is:

> a logical concurrency slot inside one queue, numbered `0..MaxParallelism-1`, owned by a job while that job holds execution capacity. 

A channel is not:

- a thread,
- a root/family lane,
- a stable hash,
- an arbitrary UI lane.

The next iteration must inspect TplQueue Core and obtain this information at the point where execution capacity is actually acquired/released.

If Core does not currently model a logical channel identity, add minimal observability instrumentation without redesigning scheduling.

See the dedicated section in `INTEGRATION.md`.

---

## 3. Waiting jobs

A waiting job may exist before it has acquired any real execution slot.

Do not fabricate a normal channel.

The next implementation must explicitly choose and document one behavior:

- `channel: null` + unassigned/waiting presentation, or
- do not place the pre-execution point on a normal channel until the real channel is known.

## 4. Detail panel contradiction resolved

Earlier integration text still mentioned forwarding selection into an existing details panel.

The UX requirement is now explicit:

**No permanent job details panel in this iteration.**

The entire available area belongs to the monitor.

`job-select` remains useful for focus and future compatibility, but it must not open or reserve space for a details panel now.

---

## 5. Theme decision

The preferred default visual style is now explicit:

**dark developer IDE / diagnostic style.**

Theme values must be centralized through CSS variables/configuration.

Do not scatter literal colors through renderer code.

---

## 6. Renderer architecture decision

Keep renderer code replaceable and minimally intelligent.

Outside the renderer keep:

- DTO validation,
- state normalization,
- channel semantics,
- graph traversal,
- search,
- collision rules,
- time mapping,
- zoom/scale policy,
- queue sizing,
- theme tokens.

This is intentional so a future renderer can be replaced without re-reviewing queue/job semantics.

---

## 7. Time-axis clarification

Use one clear mapping:

```text
older than reference time → above
reference time            → center/reference line
newer than reference time → below
```

In live-follow mode the reference time advances, causing existing jobs to move upward naturally.

Historical mode fixes the reference time and allows vertical navigation.

---

## 8. Dense queue behavior

`MaxParallelism = 15` means 15 logical channels.

Do not compress them below the configured minimum readable channel width.

Use horizontal scrolling when necessary.

Queue separators may resize sections, but minimum readable geometry remains an invariant.

## 9. Standalone demo remains required

The standalone demo is still the fastest acceptance surface.

It must run over HTTP because ES modules/imports may not work correctly through `file://`.

Expected command remains equivalent to:

```powershell
cd TplQueue.JobMonitor
node demo/server.mjs
```

Use the actual current script/port if the repository changed.
